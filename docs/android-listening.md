# Android listening insights (draft)

Imported Google Takeout watch activity and Musike playback sessions are stored in a separate IndexedDB database. Musike backups made on Android include these records. Restore merges listening records even if the library restore is set to replace; a session with an identical ID is never replaced by a shorter version. Older backups with no listening data remain valid. Android can import a Takeout ZIP directly, or a watch-history JSON file up to 100 MB. ZIP import reads only watch-history.json and music library songs.csv, skipping unrelated files. ZIP64 and split ZIP archives and HTML history are not currently supported. Saved music-library songs are stored separately from watch activity and can be played or saved as a new playlist; they are not counted as plays. Imported songs, like listening data, are included in Android backups. Takeout records can include YouTube videos that are not music; the mix uses only records explicitly tagged as YouTube Music, plus Musike playback sessions.

Listening time is measured from forward media-position progress while playback is reported as playing, capped at elapsed wall time. Seeks reset the measurement baseline. A play is counted after 30 seconds of measured listening, or half the track duration if shorter than 60 seconds. A replay creates a new session. Playback measurement depends on WebView media events; background throttling, process death, buffering, and abrupt shutdown may cause undercounting. Real Android testing is required. Takeout records do not provide verified listening durations and are never added to listening hours. A matching Takeout event and Musike session cannot reliably be matched, so imported and local counts remain separate and may overlap.

## Unfinished work

The Android Google authorization and playlist sync implementation requires device verification with configured Google OAuth credentials. It requests the YouTube read-only scope and keeps access tokens in native memory. Sync fetches owned playlists on startup, on demand and hourly while the app is visible. Synced playlists are held in memory; users can save independent local copies. An unavailable API, revoked access, or network problem leaves existing local data unchanged. Full Android lifecycle and playback testing remain outstanding. The mix is generated from available listening data when the settings view opens; saving creates a local snapshot. Imported data is not synced across devices, and its availability depends on WebView storage and backups. Google Takeout activity can be incomplete, and its JSON format, language, and available metadata vary.

The existing Android player resolves YouTube streams and provides background audio. YouTube's current API developer policies restrict separating audio from video and background playback for API clients. This existing architecture presents a potential policy and distribution blocker if official YouTube API access is added. Review it before release or claiming Play Store readiness. See https://developers.google.com/youtube/terms/developer-policies.

## Android build

Install JDK 21, Node and pnpm, and the Android SDK; set `ANDROID_HOME` or `mobile/android/local.properties`. Run `pnpm install --frozen-lockfile` and `pnpm --filter @musike/mobile apk`. The repository's existing `mobile/android/keystore.properties` or `MUSIKE_KEYSTORE*` environment variables configure release signing; otherwise the release APK is unsigned. Test on a device with the release signing identity before distributing. Never commit keystore passwords or private keys.

## Google setup (after implementation)

Enable YouTube Data API v3 and configure the OAuth consent screen and appropriate test users. Create Android OAuth clients for package `app.musike.android` and each debug/release SHA-1 signing certificate; if Google Play App Signing is used, register its app-signing certificate as well. OAuth verification and YouTube API policy review may be required before public access. No client secret should be embedded in the app. On the phone, connect, sync, revoke, reconnect, test network loss and background behavior with a real account. The official API does not expose complete watch history.

## Stable CI test signing

For reusable debug APKs, configure GitHub Actions repository secrets `MUSIKE_DEBUG_KEYSTORE_BASE64` (base64-encoded PKCS#12 keystore) and `MUSIKE_DEBUG_KEYSTORE_PASSWORD`. The keystore must contain alias `musike-debug`, using the same password for the key and keystore. This key must be separate from the release signing key. CI uses it only for debug builds and uploads the debug APK only when both secrets are present. Without either secret, CI still runs checks but skips the APK artifact; partially configured secrets fail CI. Never commit the keystore, its base64 form, or its password. A fork pull request cannot access repository secrets, so it will not upload a debug APK. Register the public SHA-1 fingerprint of the test certificate in Google Cloud. A test-signed APK cannot update an existing app signed with a different certificate; back up user data before switching installations.
